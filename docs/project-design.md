# 本地审查智能体：早期讨论记录

本文记录目前的目标、讨论过的方向和仍未确定的问题。项目处于非常初期的讨论阶段，产品形态、技术栈、集成方式和报告实现均未定案，不构成实施方案或开发任务清单。

OpenCodeReview 自身的能力与用法见 [独立知识库](open-code-review/README.md)。本文不作为上游工具的使用手册。

## 当前目标与范围倾向

- 首版在本地运行；未来可能部署，当前不处理部署方案。
- 用户指定已有 Git 仓库，自行处理认证、拉取及分支同步。
- 首版审查两个已有分支的变更，不要求提交号或时间范围选择。
- 一个业务项目可以包含前端、后端等多个仓库。
- 审查规则需要可自定义，内部框架知识以 Markdown 为主。
- 现有 Skill 可重写，无需保留其执行流程或输出格式兼容。
- 支持自定义报告结构、样式及内容组织。Markdown 不是必要中间产物。
- 优先复用 OpenCodeReview，必要时允许二次开发；是否维护 fork 尚未确定。
- 用户可接受规模可控时一次性提供相关规则和知识，不要求首版具备仓库外动态知识检索。

## 讨论过的操作流程

下面的使用流程基本符合预期，但具体页面、交互和功能边界仍可调整：

1. 选择业务项目，登记一个或多个本地仓库。
2. 为参与本次审查的仓库分别选择基准分支和目标分支。
3. 选择审查方案，关联规则与框架知识，补充本次业务背景。
4. 执行审查，查看各仓库进度及完成情况。
5. 阅读和导出报告。

一个项目的不同仓库可能使用不同的分支名称。

## 产品形态候选

产品形态没有定案。以下方向均保持开放，已有操作流程不意味着已选择“给 OCR CLI 加一个 UI”：

- 在原版 OCR 外增加应用，组织项目、方案、运行与报告。
- 二次开发 OpenCodeReview，按需要扩展其审查、结果输出或展示能力。
- 引入现有智能体，或开发一个小型报告 Agent，读取材料并生成、编辑 HTML 文件。
- 由程序直接生成 HTML，或者模型生成分析内容后再由代码模板渲染。

这些方向可以组合，不能视为互斥方案。本地服务加浏览器界面只是助手提出过的候选；是否采用、是否桌面打包及具体技术栈均未决定。

一种可能的分工是让 OCR 负责差异审查，外围应用组织输入与报告；若选择二次开发，职责划分也可能不同。原生 Viewer 和离线 HTML 可以作为参考或复用入口，是否用于最终交付仍未确定。

## 审查方案候选

讨论过用“审查方案”组织检查要求、适用文件与框架知识，也可以关联报告要求。具体保存形式、是否提供编辑界面，以及如何传给 OCR，都没有确定。

规则侧重长期检查要求，background 侧重本次业务目标、预期行为和相关框架说明。是否分开管理、如何组合，可以后续讨论。

知识内容可以考虑直接提供 Markdown 正文，也可以通过规则引导模型按需读取可访问的文档。用户接受一次性读取规则和相关知识，不要求一开始就有复杂的知识检索能力。

是否扩展知识读取工具仍可讨论，目前没有选定专门的知识库技术。

## 自定义报告需求

用户提供的《晋控项目组_0904-0912_代码审查报告.html》是内容参考，不是必须复刻的固定模板。其内容包括：

- 项目、仓库、分支范围与运行概况。
- 文件数、增删行、提交数及参与人员。
- 风险摘要、问题明细、影响及修复建议。
- 模块成果、个人工作明细和代表提交。
- 按报告所称“上传者”统计个人工作量，以及审查问题涉及或归属于哪些人员。

希望保留的重点是：报告可以超出问题列表，包含人员参与、工作量和问题归属等信息，而不必照搬样例布局。具体字段、统计口径和归属方式尚未确定。

当前讨论认为，仅有 OCR 问题 JSON 不足以支撑这类报告。缺少的数据从哪里取得、是否需要修改 OCR 输出，仍是开放问题。样例中的问题、归属和数字没有在本项目中重新核实。

## 报告实现候选

以下几种方式都讨论过，目前没有选定：

| 候选方式 | 大致思路 |
|---|---|
| 报告 Agent | 引入已有智能体，或开发小型智能体，读取材料并生成、编辑 HTML |
| 程序直接生成 | 收集报告数据，用代码或模板生成 HTML |
| 模型与模板结合 | 程序统计数据，模型撰写业务总结，再由模板排版 |
| 扩展 OCR | 二次开发其结果输出或报告能力，再决定是否需要外围生成步骤 |

“Git 采集事实 + OCR 提供问题 + 模型总结 + 模板生成 HTML”只是其中一种建议。也讨论过让模型先生成模板再复用，但用户尚未选择固定模板路线。

自定义究竟意味着修改样式、调整章节，还是通过提示词自由生成分析内容，还可以继续讨论。无需保留先 Markdown 再 HTML 的旧流程。

## 人员与工作量讨论中需要记住的区别

- Git 作者、提交者、远端推送者不是同一概念。本地 Git 数据不能直接证明谁“上传”代码。
- 问题关联修改者可由提交及行记录辅助定位，不等于缺陷责任人；跨文件、删除及多人修改需保留不确定性。
- 增删行、提交数是变更量，不等于工时或绩效。
- 最终差异增删行与逐提交累加不同；个人文件数因多人参与可重复计数，不能直接相加成项目总数。
- 前后端报告汇总不等于联合检查接口一致性。若需要联合审查，需单独定义输入和检查步骤。

## 仍开放的问题

- 产品是独立应用、OCR 的二次开发，还是二者结合？技术栈尚未讨论确定。
- 自定义报告允许多大自由度？是否需要可生成和编辑文件的报告 Agent？
- HTML 由模型直接生成、代码生成，还是采用混合方式？
- 人员工作量、问题归属和业务成果所需数据从哪里来？
- 是否需要修改 OCR 的 JSON 输出结构，还是在外层补充数据即可？用户提出的“修改 JSON 模板”仍是一种可能方向，并非决定。

这些问题用于保留讨论空间，不要求按某个顺序推进，也不表示已进入实现阶段。
